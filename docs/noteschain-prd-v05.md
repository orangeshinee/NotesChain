# NotesChain 产品需求文档 v0.4

## 极度轻量、本地优先的 Markdown 笔记工具

### 重点解决待办分散、查询不便与笔记丢失焦虑

> 每天一篇 → 一次保存 → 一次提交 → 一条可回溯的版本链

先把名字说清：Chain 指 Git 版本链。NotesChain 的 Chain 是「文件 → 保存 → Git 提交 → 历史版本」这条链，与区块链无关，也与双向链接 / 知识图谱无关。本产品**不做图谱**。旧名 LocalNotes 自 v0.3 起废止，全文统一为 NotesChain，可执行文件名为 `noteschain`。

版本：v0.5 定稿（MVP，在 v0.4 基础上收敛首页形态 + 定版日记模板 + 补齐实现级空白）  
技术选型：Rust（Axum）后端 + 网页前端（CodeMirror 6）  
日期：2026-11-01  
状态：定稿，可作为开发规格；文中标「待验证」的项必须在开发第 1 周内实测关闭，不得默认成立

> v0.4 全文存档于 `docs/archive/noteschain-prd-v04.md`，仅作对照，不再作为开发依据。

## v0.6 修订（2026-11-01，按实测反馈）

1. **目录模型**：项目根目录下分 `notes/`（Markdown）与 `assets/`（附件）两个同级目录，日记路径变为 `<root>/notes/YYYY/MM/YYYY-MM-DD.md`。兼容旧布局：若 `<root>/notes` 不存在，则把 `<root>` 当作笔记目录（v0.5 行为不变）。
2. **待办优先级**：新增 `!p0`–`!p9` 语法（与 `#标签` 分开，大小写不敏感，非法写法如 `!p10` 不识别）。首页显示按级别配色的 P 徽标，支持「按优先级」排序（无优先级垫底）；`raw_line` 保留原始文本，不影响回写定位。
3. **编辑器默认预览**：打开笔记先进入只读渲染视图，需要修改时点「编辑」切到 CodeMirror。
4. **新建笔记带元数据**：模板增加 YAML frontmatter（`title` / `type` / `created` / `tags`）。日记模板 = frontmatter + 四个二级标题；普通笔记模板 = frontmatter + 标题行。**仅用于新建文件**，不改写已有文件。
5. **模板目录与占位符**：模板放在项目根 `templates/*.md`，支持 `{{TITLE}}` / `{{DATE}}` / `{{DATETIME}}` / `{{TAGS}}`；「新建」可选择日记 / 普通笔记 / 任意自定义模板，选日记时可指定日期（生成那天的日记）。日程段标题由「今日日程」改为「日程」，解析器兼容两者。
6. 其余实测反馈与处理见 `docs/issues-v0.2.md`。
7. **界面改版（2026-11-02，样式收敛）**：统一到「纸感」主题——暖纸底 + 墨绿，正文版心 680px，标题改用系统宋体（不打包字体）；字号收敛为 6 档、圆角收敛为 3 档，颜色语义收口（绿色只表示进行中/成功）。侧边栏快捷入口只留 首页 / 今天 / 新建，历史、宽屏、刷新、重建索引收进「⋯」。首页待办表删掉与正文重复的「标签」列（标签仍在事项文本内，点击可筛选）；列宽记忆改用 `nc.todoCols.v2`。同名笔记在文件树里补显示所在目录。编辑器当前行由整行灰底改为左侧细标记，标题字号与预览对齐。暗色主题不在本次范围内，仅修掉硬编码颜色造成的对比度问题。

## v0.5 相对 v0.4 的变化（本版修订）

1. **首页形态定版，取消折叠机制**（第 4.1 节）：首页固定为「日程区 + 全部待办」两段。日程区支持**本日 / 本周 / 本月**三档切换，**默认本周**；待办区**一次列出全部未完成待办**，不折叠、不按目录分区，`raw/` 的待办并入同一列表。v0.4 的「近 30 天折叠 + 展开全部」整段废止。
2. **日程提取从「当日单文件」扩展为「区间多文件」**（第 3.3 节）：本周 / 本月视图须读取区间内所有日记文件的 `## 今日日程` 段。这是第 1 条的直接后果——不补这条，本周视图无从实现。
3. **每日文件新建模板定版**（第 3.1.4 节 + `docs/templates/daily-note.md`）：新建即写入骨架（`# 日期` + 三个二级标题）。v0.4 只写了「不存在则新建」，没写新建内容，导致第 3.1.2 节的内容兜底判定对自家新建的文件不成立。
4. **性能指标降级为参考目标**（第 8 章）：空载内存由硬指标 `< 20 MB` 改为**参考目标**，不再作为发布门槛；前端产物体积预算推迟到收尾阶段再定（先做功能，最后统一精简压缩）。
5. **补齐 v0.4 遗留的实现级空白**：三级就近匹配的「距离」定义（第 3.2.3 节）、日程高亮刷新间隔与疑似日程提示范围（第 3.3 节）、API 响应体与错误码规范（第 7.3.1 节）、待办列表排序规则（第 4.1 节）。

## v0.4 相对 v0.3 的核心变化

1. **目录结构定版为三类子目录**（第 3.1 节）：`YYYY/MM/` 时间序列、`raw/` 主题命名空间、`assets/` 附件区。v0.3 只定义了「每天一个文件」，没有给主题笔记和附件留位置，本版补齐。
2. **图片与附件路径改为双轨解析**（第 3.1.3 节）：先按文件自身相对路径解析，找不到再按 notes 根目录解析。兼容标准 Markdown 写法与根基准写法，不批量改写已有文件。
3. **新增双链（P1，默认关闭 / 实验性）**（第 3.5 节）：`[[目标]]` 语法与解析规则定版，含 `/` 走路径、不含 `/` 走 `raw/` 裸名。支持日记互链与主题笔记互链；砍序第 1 位，不阻塞 P0 交付。
4. **待办定位协议改写**（第 3.2.3 节）：从「文件 + 行号」改为「文件 + 行号 + 原始行文本」的三级解析，消除外部插入行导致的改错行。
5. **补齐 v0.3 遗留的语义空白**（第 0 章 11 条逐条落决策或限制）：红线与降级的关系、静态资源鉴权落地、重建索引接口、文件列表分组等。
6. **第 10.2 节范围调整**：「双向链接 / 图谱」中的**图谱仍在范围外**，但双向链接移入 P1。

## 0. 批判性回顾：v0.3 留下了什么问题

先说结论：v0.3 是一份规则完备的 PRD，但它把「一份文件装所有日记」当成了默认形态，导致三处结构性缺口——主题笔记无处安放、附件路径没有基准、待办定位没有防漂移。这三处都不是 v0.3 写错了细节，是**模型少了一层**。v0.4 补这一层，不再做无边界的功能扩张。

本章把 v0.3 遗留的 11 个问题摆到台面上，每条只给三种结局之一：已决策（正文写死）、明确限制（做不到就明说）、待验证（给验证方法和关闭时间）。不接受「后续再看」式的回避。

| 问题                                         | v0.4 的处理                                                                       | 落点        |
| ------------------------------------------ | ------------------------------------------------------------------------------ | --------- |
| 1. 目录结构只有「日记」一种文件，主题笔记无处安放                 | 定版三类子目录：`YYYY/MM/` 时间序列、`raw/` 主题命名空间、`assets/` 附件区，各自的扫描 / 待办 / 标签 / 双链权限逐项写死 | 第 3.1 节   |
| 2. 图片与附件的路径基准未定义                           | 定为双轨解析：先按文件自身相对路径，找不到再按 notes 根解析；不改写已有文件                               | 第 3.1.3 节 |
| 3. 待办回写只靠行号定位，外部插入行会改错行                    | 改为「行号 + 原始行文本」三级解析：行号命中 → 全文匹配（唯一则改写，多处则行号就近）→ 仍无法区分才拒绝写入并提示                                     | 第 3.2.3 节 |
| 4. 「红线：Git 不可砍」与「无 git 降级 / 同步盘关闭 Git」自相矛盾 | 区分「发布前提」与「运行期容错」：无 git / 同步盘环境下**延期发布**，降级只用于运行中途环境突变                          | 第 1.3 节   |
| 5. 静态资源（图片）无法带 token 头，鉴权会 401             | 定版：首次访问页面时种 Cookie，后续所有请求走 Cookie；URL query 只作首次引导                             | 第 9.1 节   |
| 6. 「手动重建索引」有入口无接口                          | 补 `POST /api/index/rebuild`                                                    | 第 7.3 节   |
| 7. 「目录结构完全一致、无痛迁移」措辞过宽                     | 精确化：Markdown 内容无损，但 SB 专属语法降级为纯文本、文件位置不强制                                      | 第 2.3 节   |
| 8. 完成标记的剥离边界未定义                            | 定版：以 `✅` 为分隔符，从 `✅` 到行尾整段剥离                                                    | 第 3.2.2 节 |
| 9. 后端未写明按文件串行化写入                           | 定版：同一文件的全部写操作串行化，不同文件并行                                                        | 第 5.3 节   |
| 10. 首页待办列表无规模上限假设                          | v0.4 定为「近 30 天折叠 + 展开全部」；**v0.5 废止折叠**，改为全量渲染 + 虚拟列表，见第 4.1 节 | 第 4.1 节   |
| 11. 双链在范围内还是范围外没有中间态                       | 定版：双链入 P1 且默认关闭（实验性），砍序第 1 位；图谱仍在范围外；解析规则一次写死，不留特例                                                | 第 3.5 节   |

一条总原则：凡是 v0.3 写了名字却没写规则的地方，v0.4 要么补规则，要么降为 P1 或明确不支持。不允许把模糊带进开发——模糊在 PRD 里省下的半天，会在联调时以一周返工的形式收回来。

## 1. 范围治理：P0 / P1 分层与可砍线

v0.4 的 MVP 仍是一个有明确底线的主线产品。P0 是「不做就不能平替、不能防丢」的底线；P1 是「做了更好，砍掉不影响主线成立」。

| 功能                           | 层级 | 说明                         |
| ---------------------------- | -- | -------------------------- |
| 首页待办汇总 + 勾选回写 + 完成时间         | P0 | 核心闭环，任何情况下不砍               |
| 页内编辑 + 自动保存 + 冲突提示           | P0 | 不砍；cleanMode 可降级（见第 5 章）   |
| Git 检测、自动 init、防抖自动提交、上次提交时间 | P0 | 防丢靠它                       |
| 多级标签树 + 按标签过滤                | P0 | 用户的分类主线，不砍                 |
| 全文搜索（子串）+ 标签 / 状态过滤          | P0 | 不砍；排序与分词不做（第 4.5 节）        |
| 三类子目录结构与图片双轨解析               | P0 | v0.4 新增，目录语义是本版模型的地基       |
| 日程视图（本日 / 本周 / 本月，默认本周） | P1 | 可降级为「只显示本日、原样列出日程段」        |
| cleanMode L2（表格、图片行内大图、链接渲染） | P1 | L1 先行，L2 后补（第 5.2 节）       |
| Git 历史浏览、diff、回滚入口           | P1 | MVP 只显示上次提交时间，历史用命令行看      |
| 标签计数、待办按标签统计                 | P1 | 树本身是 P0，计数可后补              |
| 双链 `[[目标]]` 解析与跳转            | P1 | v0.4 新增，默认关闭（实验性），见第 3.5 节；不阻塞 P0 交付 |

### 1.1 可砍顺序（时间不够时，按此顺序砍，不许乱砍）

1. 先砍双链（整节 P1）——默认关闭、实验性，砍掉不影响任何 P0 能力；笔记仍是纯 Markdown。
2. 再砍 Git 历史浏览 / diff / 回滚 UI——命令行 `git log` 能顶。
3. 再砍日程视图的跨日聚合（本周 / 本月），退化为只显示本日日程段，且不排序、不高亮、不算时长——内容不丢。
4. 再砍 cleanMode L2 元素——表格、图片在编辑态只显示语法，预览态正常渲染。
5. 最后砍标签计数与搜索结果高亮片段——过滤与跳转保留。

红线：待办闭环、自动保存、Git 自动提交、多级标签过滤、目录结构与图片双轨解析这五项砍掉任何一项，本版定稿就不成立，应延期而不是降级发布。一个「能看不能勾、写了会丢、图挂不上」的版本比晚一周更伤。

### 1.2 产品目标（沿用，补一句边界）

为个人用户（尤其是数据分析师、写 SQL、做项目管理的人群）提供一个极简、高效、低资源占用的本地笔记系统，替代当前基于 Silver Bullet（Node.js 后端）的笔记服务。核心价值：纯 Markdown 无格式锁定；一键汇总并处理全部未完成待办；多级标签区分项目与事物；Git 自动提交留住每一次修改的历史；双链（默认关闭的实验性 P1）可把日记与主题笔记连起来。

边界同样重要：它只做「每日记录 + 待办 + 标签 + 搜索 + 版本链」这一条主线（双链为默认关闭的实验性扩展），不做通用笔记平台，不做图谱。

### 1.3 发布前提与运行期降级的关系（v0.4 新增，v0.5 沿用）

v0.3 一边写「砍掉 Git 自动提交则 v0.3 不成立，应延期」，一边写「检测不到 git 就降级，笔记功能照常工作」。两条放在一起无法执行：到底该延期还是该降级发布？

v0.4 把两件事分开：

**发布前提（决定能不能发）**：目标环境必须满足两条——① 已安装 git 且版本可用；② 笔记目录**不在** OneDrive 等同步盘内。任一条不满足，本次不发布，按红线延期，而非降级发布。

**运行期降级（决定发出去之后怎么表现）**：软件启动后才发现环境与前提不符（例如用户把目录挪进了同步盘，或 git 被卸载），此时降级为「笔记 / 待办 / 编辑 / 搜索全部照常，仅关闭自动提交」，界面明确提示「未检测到 git，版本历史未启用」或「目录位于同步盘内，Git 自动提交已暂停」，不报错、不阻断启动。

判定时点：开发第 1 周在目标云桌面实测并记录（见附录 B），实测结论写入测试报告，作为放行依据。

## 2. 目标用户、真实工作流与平替边界

### 2.1 目标用户

主要使用 Markdown 记录日常工作、会议、SQL 脚本和待办的个人用户。不希望使用 Obsidian 等重型工具；需要在公司云桌面环境稳定运行。追求简单、可控、可长期维护的本地方案；笔记目录现状为 Silver Bullet 管理的纯 Markdown 文件。

### 2.2 日常工作流（产品必须贴合的行为）

1. 每天一个文件：每天生成一个 Markdown 文件，记待办和日常记录，路径见第 3.1 节。
2. 先看首页：打开网页先看本周日程（可切本日 / 本月）和历史全部未完成待办。
3. 勾掉即完成：在首页或正文里点勾，记录完成时间，该待办随即从未完成列表消失。
4. 标签分类：用 1-3 级嵌套标签区分这件事属于哪个项目、哪类事物。
5. 网页内直接写：点进某一页就能编辑，不跳外部编辑器；保存即落盘并进入 Git 提交队列。
6. 随手搜：全文搜索能直接定位到内容、标签和待办。
7. 主题笔记另放：跨天的专题内容（项目复盘、SQL 备忘、口径说明）不塞进日记，放 `raw/` 下；双链开启时可从日记指过去，未开启时用普通路径链接或直接打开文件。

对比项 Silver Bullet（现状） vs NotesChain

| 对比项  | Silver Bullet（现状） | NotesChain                      |
| ---- | ----------------- | ------------------------------- |
| 后端   | Node.js 服务        | Rust 单文件可执行程序，空载内存目标见第 8 章（含测法） |
| 数据   | 纯 Markdown        | 纯 Markdown，目录结构与现状兼容，可迁移        |
| 汇总方式 | Lua 查询 / 插件，任意可编程 | 固定的待办、标签、日程三种汇总，不可编程（见 2.3）     |
| 版本历史 | 无内建版本链            | Git 自动提交，本地版本链                  |
| 链接   | Wiki 链接（较重）       | 轻量双链 `[[目标]]`（P1，默认关闭 / 实验性），只做定位与跳转，无图谱       |
| 范围   | 通用笔记平台，带插件生态      | 只做每日记录这一条主线，不做平台                |

### 2.3 平替边界：明确放弃的 Silver Bullet 能力

把话说在前面：NotesChain 不是 Silver Bullet 的功能等价替代。Silver Bullet 的待办汇总靠的是可编程查询——用户能自己写条件、拼看板、改口径。NotesChain 用硬编码的解析规则换零配置，代价就是灵活性。以下能力在 MVP 明确放弃，用户须知情：

- **任意查询**：不能写「近 7 天新建且带某两个标签的待办」这类组合查询；只能用产品给定的标签过滤 + 关键词过滤 + 状态过滤。
- **自定义看板与聚合**：不能按周统计完成数、不能自定义首页区块、不能把查询结果存为一个页面。
- **插件与脚本**：没有插件系统、没有模板引擎、没有自动化脚本钩子；在 Silver Bullet 里靠插件实现的小自动化，平替后全部消失。
- **富查询语法**：正文里的查询块、数据表达式不会被执行，只会当普通文本显示。
- **图谱与关系视图**：不做节点图、不做力导向布局、不做关系可视化。双链只提供定位、跳转和反向链接列表。

**迁移精确化（v0.4 修订，取代 v0.3 的「目录结构与现状完全一致，可无痛迁移」）**：迁移后 Markdown 正文内容无损，但有两点必须让用户知情——① Silver Bullet 专属语法（查询块、嵌入表达式、SB 特有 frontmatter 字段）会降级为普通文本，不报错也不执行；② 文件位置不强制迁往 `YYYY/MM/`，用户可保留现有布局，NotesChain 扫描所有 `.md` 并按路径优先、内容兜底判定文件类型（见第 3.1.2 节）。

平替验收的正确问法不是「功能是否一样多」，而是第 10 章那一条：现有目录原样启动，首页待办、标签、编辑、搜索、Git 提交五件事都成立，且用户日常真正用到的查询不超过给定过滤能力。开发第 1 周须先盘点用户在 Silver Bullet 里实际在用的查询与插件清单，超出上表范围的，逐条确认放弃或列入 P1——这一步不做，平替风险不关闭。**待验证**

## 3. 文件与数据规范

### 3.1 目录结构：三类子目录

```
notes/
├── 2026/
│   └── 10/
│       ├── 2026-10-01.md      ← 日记（时间序列）
│       └── 2026-10-02.md
├── raw/
│   ├── 供应链.md                ← 主题笔记（人起的名字）
│   └── KPI口径.md
├── assets/
│   ├── image.png               ← 图片与附件
│   └── file.pdf
└── .git/                       ← NotesChain 自动维护，界面与搜索一律忽略
```

每日文件路径固定为 `YYYY/MM/YYYY-MM-DD.md`，月份用两位数字，示例：`2026/10/2026-10-01.md`。打开首页时，当天文件不存在则按此路径自动新建（文件夹不存在一并创建），新建动作同样进入 Git 提交队列。

`raw/` 与 `assets/` 由用户按需创建，程序不强制生成（首次用到时提示创建）。`raw/` 下允许子目录，笔记文件为 `.md`。

**为什么切分粒度定为「按天」**：日记文件越小，Git 版本粒度越细（可按天回滚）、外部编辑的冲突半径越小（一次只影响一天）、行号漂移的破坏面越小。代价是文件数量一年约 365 个——这一条由第 4.6 节的文件列表分组折叠来化解，不构成问题。

#### 3.1.1 三类子目录的权限表（v0.4 新增，必须逐字实现）

| 子目录        | 语义            | 扫描 | 提取待办 | 提取日程 | 计入标签 | 双链目标         |
| ---------- | ------------- | -- | ---- | ---- | ---- | ------------ |
| `YYYY/MM/` | 时间序列，按日期自动生成  | ✅  | ✅    | ✅    | ✅    | ❌（只能被路径形式指向） |
| `raw/`     | 主题命名空间，文件名由人取 | ✅  | ✅    | ❌    | ✅    | ✅（裸名与路径均可）   |
| `assets/`  | 二进制附件         | ❌  | ❌    | ❌    | ❌    | ❌            |

说明：`raw/` 里的待办**计入首页汇总**（与标签的统一索引原则一致）；`raw/` 里不解析日程（没有「当日」概念）。

#### 3.1.2 文件类型判定：路径为主，内容兜底（v0.4 定稿修订）

为兼容用户现有 Silver Bullet 目录（其布局未必是 `YYYY/MM/`），后端按以下顺序判定文件类型：

- **主规则（路径）**：相对路径形如 `YYYY/MM/YYYY-MM-DD.md`（如 `2026/10/2026-10-01.md`），且文件名日期与路径年月一致 → 判定为**日记文件**，参与日程解析与「今日」判定；
- **兜底规则（内容）**：路径不匹配时，若文件首个标题行形如 `# YYYY-MM-DD`（如 `# 2026-10-01`，与附录 A 示例的标题格式一致）→ 同样判定为**日记文件**；
- 其余 `.md` 文件 → 判定为**普通笔记**，参与待办、标签、搜索，但不参与日程。

`raw/` 与 `YYYY/MM/` 是**推荐布局**而非硬约束。这样用户既可以按本版规范整理，也可以原样沿用旧目录，两种都能正常工作。

#### 3.1.3 图片与附件路径：双轨解析（v0.4 定稿修订）

**规则**：所有 `.md` 文件中的图片与附件引用，按以下顺序解析，命中即停：

1. **先按文件自身相对路径解析**（标准 Markdown 语义）：如位于 `2026/10/` 的日记写 `![](../../assets/image.png)`，按标准相对路径计算；写 `![](images/a.png)`，先找该文件同目录体系下的 `images/a.png`；
2. **找不到再按 notes 根目录解析**：如 `![](assets/image.png)`，在相对路径未命中时按 `notes/assets/image.png` 查找。

两种写法都合法：

```
✅ 标准相对写法（相对文件自身）：
   ![](../../assets/image.png)     ← 位于 2026/10/ 的日记
   ![](images/a.png)               ← 图片在文件同目录体系下

✅ 根基准写法（相对 notes 根）：
   ![](assets/image.png)           ← 无论文件在哪一层
   [报告](assets/report.pdf)
```

**为什么双轨**：草稿曾定「一律以根为基准」，代价是现有文件要批量改写，且与第 10.1 节「不改动已有文件」的平替标准自相矛盾。双轨同时保住两边：旧文件按标准语义原样可读、一个字不用改；新文件可用根基准写法省去 `../../`。不做任何批量改写。

**歧义处理（定版）**：若同一引用按相对路径与按根路径都能命中、且指向不同文件，相对路径优先（先命中先停），并在渲染日志中记录一次提示；用户改用另一种写法即可消除歧义。

**实现要求**：后端渲染与静态文件服务统一走上述双轨顺序；解析结果仍须落在 notes 根目录内（第 9.2 节），指向根外的相对路径一律拒绝。前端不得自行拼接路径。

#### 3.1.4 每日文件新建模板（v0.5 定版）

打开首页或点击「今天」时，若当天文件不存在，按第 3.1 节的路径新建，**并立即写入以下骨架**（不是空文件）：

```markdown
# YYYY-MM-DD

## 今日日程

## 待办

## 记录
```

其中 `YYYY-MM-DD` 替换为当天日期（与文件名日期一致），三个二级标题各占一行、标题下不留空行内容。骨架的权威副本为 `docs/templates/daily-note.md`，实现时把同一份字符串内嵌进二进制（`include_str!`），**不读取运行时外部模板文件**——避免用户目录里缺模板就新建失败。

**为什么必须定死模板**（v0.5 补，消解 v0.4 的空白）：

- 第 3.1.2 节的**内容兜底判定**依赖「首个标题行形如 `# YYYY-MM-DD`」。若新建的是空文件，NotesChain 自己生成的日记就永远不满足兜底规则——用户把笔记目录换一种布局后，自家新建的文件会被判成「普通笔记」，日程整段丢失。
- 第 3.3 节的日程提取依赖 `## 今日日程` 标题存在。空文件虽然只是「无日程」，但用户不知道该往哪写，实际会自己造标题，标题写错（`## 日程`）就静默漏检。
- 三个标题同时也是用户心智：日程、待办、记录各归其位，首页三块汇总的边界才清晰。

**限制（明确不做）**：不做模板自定义、不做变量替换（除日期外）、不做「从昨天复制未完成待办」。模板是固定的四行骨架，用户可在自己已有的文件里随便改结构——解析规则不依赖骨架，只依赖标题与语法本身。

### 3.2 待办语法与完成格式

**3.2.1 语法**

```markdown
- [ ] 发供应链周报 #工作/供应链
- [x] 回复供应商邮件 #工作/采购 ✅ 2026-11-01 09:12
```

唯一来源：未完成待办只认行首（允许缩进）的 `- [ ]`；代码块内的 `- [ ]` 不算待办。

**todo: 正式删除**（沿用 v0.3 决定，v0.4 无变化）：待办只认 `- [ ]`，不保留 `todo:` 双轨。理由是正文随手写的 todo 会被误收，且双轨会让「到底什么算待办」永远说不清。代价明示：历史文件里以 `todo:` 写的事项不会进入汇总。补救：首次启动时做一次性扫描，把命中的 `todo:` 行列成迁移清单展示给用户，由用户决定是否手工改成 `- [ ]`；程序不自动改写历史文件。**已确认 · 2026-11-01**

**嵌套**：缩进的待办独立计数、独立勾选；勾选父项不自动勾选子项，子项全部完成后也不自动完成父项。首页汇总时保留层级缩进显示。

**完成回写**：勾选时后端只改该行：`- [ ]` 改为 `- [x]`，行尾追加完成标记（对勾符号 `✅` + `YYYY-MM-DD HH:mm`）；不重排、不格式化其他行。取消勾选时移除行尾完成标记，恢复为 `- [ ]`。

**循环待办**：不支持。MVP 不做「每周一自动生成」这类循环语义；需要重复的事项由用户手工复制。写了「每周」「每月」等字样只当普通文本。

**优先级与截止日期**：不设字段。MVP 不解析优先级符号，也不解析截止日期；文本里写的日期只当普通文本显示，不参与排序与提醒。如后续要加，须另立规范，不得靠猜测解析。

#### 3.2.2 完成标记与搜索的隔离（v0.4 补齐剥离边界）

完成标记是机器追加的内容，会污染全文搜索——例如搜日期会命中一堆完成时间。因此规定：**搜索与索引在匹配前剥离行尾的完成标记段；完成时间只在「已完成」过滤视图里作为结构化字段展示，不进关键词索引。**

**剥离边界的精确定义（v0.4 新增，消解 v0.3 的模糊）**：以 `✅` 字符为分隔符，从该字符起至行尾（含 `✅` 本身与随后的时间戳）整段剥离。剥离只作用于**已完成的待办行**（行首为 `- [x]`）。因此：

- `- [x] 回复供应商邮件 #工作/采购 ✅ 2026-11-01 09:12` → 剥离后参与索引的文本是 `- [x] 回复供应商邮件 #工作/采购`
- 未完成行内出现的 `✅` **不剥离**（用户自己写的 emoji 不应被吞掉）
- 剥离后若行尾仍有空白，一并去除

#### 3.2.3 待办定位协议（v0.4 改写，消解「行号漂移改错行」）

**问题**：v0.3 规定待办回写按「文件 + 行号」定位。若用户在 NotesChain 之外（VS Code 等）于同一文件上方插入若干行，则磁盘上原第 N 行已不是该待办，后端照行号写入会**改错行**，且原待办未被勾掉——这是 P0 正确性问题，不是体验问题。

**v0.4 方案（对齐 Obsidian Tasks 插件 `findLineNumberOfTaskToToggle` 的三级策略，不引入行哈希）**：

前端提交时携带四项：**文件路径 + 行号 + 该行的原始文本 + 文件版本号**。

其中「原始文本」定义为：**该行去掉行尾完成标记后的整行文本**（含 `- [ ]` / `- [x]` 状态符）。

后端解析三级：

| 级别       | 判定条件                   | 动作                                                        |
| -------- | ---------------------- | --------------------------------------------------------- |
| 一级（快路径）  | 文件中第 N 行的内容 == 提交的原始文本 | 直接改写该行。绝大多数情况命中，O(1)                                      |
| 二级（兜底）   | 一级不命中；在全文中查找内容等于原始文本的行 | **恰好一处**匹配 → 改写该处（外部插入行后仍能正确定位）；多处匹配 → 进入三级就近匹配；零匹配 → 进入三级拒绝           |
| 三级（就近 / 交还用户） | 多处匹配或找不到               | 多处匹配时先**就近匹配**：取与提交行号距离最近的那一处改写（同文件出现两条完全相同的待办时靠这一条区分）；若最近距离并列、仍无法唯一区分，或零匹配 → **拒绝写入**，返回明确错误「该待办已不存在或内容已变更，请重新加载」，界面提示用户；**不猜、不静默改错行** |

**「就近」的距离定义（v0.5 补）**：距离 = **提交行号与该候选行行号之差的绝对值**（|N − M|），不做加权、不比较内容相似度。多条候选距离相同（并列最近）时按三级规则**拒绝写入**，不取第一条。

**并发守卫**：复用第 5.3 节已有的版本号（mtime + 内容哈希）。版本号不一致时说明文件已被外部改过，此时**不直接拒绝**，而是走二级解析尝试重新定位——这是本条与 v0.3 的关键区别：v0.3 的版本号协议只保护整文件保存，本版把它扩展到待办回写。

**取消勾选的特例**：勾选后行尾追加了 `✅ 时间戳`，原始文本随之变化。因此比对必须基于「去掉完成标记后的原始行」——前端提交的原始文本始终是**未追加完成标记时**的那一行，取消勾选时同样按此比对，否则永远匹配不上。

**行号的作用**：行号在一级判定中只是**快路径提示**，真相靠文本比对。这与 Obsidian Tasks 的取舍一致——行号会漂，文本不会。

### 3.3 日程语法：严格格式 + 漏检必须可见

```markdown
## 今日日程

- 15:00-17:00 供应链周会 #工作/供应链
- 09:30-10:00 晨会 @线上
- 15:00 提交月报
- 记得带电脑充电器
```

日程只从**日记文件**的 `## 今日日程` 段落提取；**提取范围由首页视图决定**（v0.5 定版）：本日视图只读当天文件；本周视图读本周一至周日的全部日记文件；本月视图读当月 1 日至月末的全部日记文件。日记文件按第 3.1.2 节判定；区间内某天文件不存在时按「无日程」处理，不报错、不提示缺文件。会议名称由用户从 Outlook 同步后手写，NotesChain 不接 Outlook API。`raw/` 下的主题笔记不解析日程（见第 3.1.1 节）。

行首为 `HH:mm-HH:mm`（24 小时制）即时间段日程；只有 `HH:mm` 即时间点日程；后面跟名称，可选标签与 `@地点`。不识别「下午 3 点到 5 点」等自然语言时间。

日程不是待办：不用勾选，到点即过；待办必须勾掉才消失，两者严格分开。


**必须承认的脆弱性**：这套解析只认一种写法。标题写成 `## 日程`、时间写成 `15:00~17:00`、日程写在 `raw/` 里，都会漏掉——而且 v0.2 的设计是静默漏掉，用户只会觉得「今天怎么没会」。v0.3 起定三条兜底：

1. **未识别行诊断区**：`## 今日日程` 段里不符合时间格式的行（如上例「记得带电脑充电器」）不进时间线，但原样列在时间线下方并标「未识别时间」，绝不丢弃、绝不静默；
2. **疑似日程提示**：当日文件其他段落里出现行首时间样式的行，首页给一条弱提示「有 1 行像日程但不在日程段内」，只提示、不自动挪动；
3. **手工漂移已知情**：会议名靠从 Outlook 手工复制，改期、取消不会自动同步，日程以用户手写为准——这是接受的限制，不假装能解决。

**明确不支持**：全天日程、跨天日程、时区换算。所有时间一律按本机本地时间朴素解释；出差跨时区时日程显示可能与 Outlook 不一致，属已知限制。

时间段结束早于开始（如 `17:00-15:00`）视为未识别行，进诊断区，不猜测修正。

#### 3.3.1 视图范围、排序、高亮与诊断范围（v0.5 新增）

**三档视图的时间边界**（一律本地时间，不做时区换算）：

| 视图 | 范围 | 读取文件 |
| --- | --- | --- |
| 本日 | 当天 00:00–23:59 | 当天日记文件 |
| 本周（默认） | ISO 周，周一 00:00 – 周日 23:59 | 本周 7 天的日记文件（存在几个读几个） |
| 本月 | 当月 1 日 00:00 – 月末 23:59 | 当月最多 31 个日记文件 |

**分组与排序**：按天分组，组标题为 `周一 · 10/27` 形式（今天显示为 `今天 · 11/01`）；组内按开始时间升序，时间点日程（只有 `HH:mm`）按其时刻插入同一序列，排在同时刻的时间段之前；同刻同名保持文件内出现顺序（稳定排序）。

**高亮与置顶**：今天所在分组**置顶**并高亮；组内**正在进行**的日程（当前时间落在起止区间内）加「进行中」标记并排到该组最前；已过去日期整组灰显但不隐藏；未来日期正常显示。无「跨天进行中」概念——23:59 之后一律按结束处理。

**刷新间隔（v0.5 定版）**：前端每 **60 秒**重算一次「进行中 / 已结束」状态与当前时间指针，**不重新请求接口**（数据未变）；本地日期跨零点时，整页数据刷新一次并切到新的一天。

**诊断区范围**：未识别行诊断区只在**本日视图**完整展开（针对当天文件，原样列出未识别行）。本周 / 本月视图不展开诊断区，只在对应日期分组末尾显示一行摘要「N 行未识别」；点击摘要切到本日视图查看原文。已过去日期的未识别行同样只给摘要——诊断区的用途是提醒今天别漏会，不是历史考古。

**疑似日程提示的范围**：只检查**当天日记文件的其他段落**里出现行首时间样式的行，不检查 `raw/`、不检查其他日期文件，避免在首页堆一堆历史噪音。

### 3.4 标签语法与治理

格式：`#一级/二级/三级`，最多 3 级，如 `#工作/供应链/KPI`；可出现在正文与待办行中。

**字符规则**：允许中文、英文字母、数字、连字符与下划线；不允许空格——空格即标签结束；不允许以 `/` 开头或结尾、不允许连续 `//`。不符合规则的 `#` 串不当标签。

**排除规则**：代码块、行内代码中的 `#` 不算标签；标题行首的 `#` 不算标签；纯数字话题（如 `#2026`）仍算标签，不做特殊豁免，避免规则分叉。

**统一索引**：笔记标签与待办标签是同一个索引。一条待办上的标签既能在标签树里点到，也计入该标签的笔记与待办计数；不存在「待办专用标签」。`raw/` 下的笔记标签同样进入统一索引。

**层级语义**：点一级标签，包含其全部子标签的内容；点三级标签，只看该叶子。

**治理的实话**：改名、合并、删空标签在 MVP 不提供工具。改名只能靠外部编辑器全局查找替换（会正常触发文件监听与 Git 提交，历史可查）。代价明示：标签写错、写出近义两套（如 `#工作/供应链` 与 `#工作/供应`）时，MVP 阶段只能手工收拾；产品只做一件事——标签树里把零笔记的空标签置灰，让问题至少看得见。若盘点发现标签混乱已是高频问题，再把「批量改名」提为 P1，不得默默膨胀进 MVP。

### 3.5 双链语法与解析规则（v0.4 新增，P1，默认关闭 / 实验性）

**启用方式（定版）**：双链默认关闭。须在启动参数或设置中显式开启（实验性开关）后，才解析 `[[ ]]`、才启用出链 / 反向链接接口与反向链接面板；关闭时 `[[ ]]` 按普通文本显示，不影响任何 P0 能力。双链在砍序中排第 1 位（第 1.1 节），不阻塞 P0 交付与验收。

#### 3.5.1 语法

```markdown
今天复盘了 [[raw/供应链]]，口径见 [[raw/KPI口径]]。
明天继续 [[2026/10/2026-10-02]] 的跟进事项。
附件在这里：[[assets/report.pdf]]
```

`[[` 与 `]]` 之间为链接目标。链接目标**不含**空格与换行；目标内的 `/` 为路径分隔符。代码块与行内代码中的 `[[ ]]` 不解析。

#### 3.5.2 解析规则（定版，无特例）

| 目标形式                             | 解析方式                              | 说明                             |
| -------------------------------- | --------------------------------- | ------------------------------ |
| 含 `/`，如 `[[2026/10/2026-10-02]]` | **路径解析**：以 notes 根目录为基准定位         | 可指向日记文件、`raw/` 笔记、`assets/` 附件 |
| 不含 `/`，如 `[[供应链]]`               | **裸名解析**：仅在 `raw/` 下按文件名（不含扩展名）查找 | 人起的名字在 `raw/`，日期是系统生成的，两者不混    |

**`.md` 扩展名可省略**：`[[raw/供应链]]` 与 `[[raw/供应链.md]]` 等价。

**日记互链**：形如 `[[2026/10/2026-10-02]]` 的路径指向日记文件，点击后跳转并**定位到该文件的日期标题行**（`## 2026-10-02`），而非文件首行。

**裸名不解析日记**：裸名只在 `raw/` 下查找，日期形式的裸名（如 `[[2026-10-02]]`）**不命中**任何目标，渲染为未命中样式。原因：日记文件由日期生成、可能位于任意层级，用路径表达才唯一；裸名空间专属于人起的名字。这条一次性堵死「裸名该指日记还是指 raw」的歧义。

#### 3.5.3 命中与未命中

| 情形                | 渲染                     | 行为                                                          |
| ----------------- | ---------------------- | ----------------------------------------------------------- |
| 命中                | 蓝色链接样式                 | 点击跳转目标文件；指向日记时定位到日期标题行                                      |
| 未命中               | 虚线 / 灰色占位样式，与正常链接视觉可区分 | 点击弹出「创建 raw/供应链.md？」，确认后在 `raw/` 下新建空文件并跳转；指向路径形式的同理，在该路径创建 |
| 指向 `assets/` 下的附件 | 链接样式                   | 点击由静态服务打开文件（不进入编辑器）                                         |

#### 3.5.4 命名空间与冲突处理

- **同名冲突**：`raw/` 内若存在两个解析到同一裸名的文件（如 `raw/A.md` 与 `raw/sub/A.md`），**启动时告警并列出冲突文件路径，但不拒绝启动**；冲突期间这些裸名不解析（渲染为未命中样式并标注冲突），须改用路径形式（如 `[[raw/sub/A]]`）指向，用户改名消除冲突后裸名自动恢复。理由：两个同名文件不该让全部笔记都打不开；同时也不静默取第一个，避免点进错误的笔记。
- **日记与 `raw/` 不会撞**：日记只能被路径形式指向，`raw/` 只能被裸名或路径形式指向，两类命名空间不重叠。
- **大小写与空格**：**大小写敏感、空格敏感**，文件名精确匹配。

#### 3.5.5 明确不支持

- 不做图谱 / 节点关系视图 / 力导向布局。
- 不做别名语法 `[[目标|显示文本]]`——目标即显示文本，多一层语法就多一类解析歧义。
- 不做标题锚点 `[[目标#小节]]`。
- 不做 `[[ ]]` 指向非 `.md` 以外的富文本格式（`.txt` 等按附件处理）。

## 4. 核心功能

### 4.1 首页工作台（Dashboard）P0

打开即达，是默认落地页，不需要先选文件。顶部显示 Git 状态：上次提交时间与待提交变更数（第 6 章）。

**上方：日程区（v0.5 改版）**——三档切换 `本日 / 本周 / 本月`，**默认本周**。分组、排序、高亮、刷新与诊断范围见第 3.3.1 节。该区域整体为 P1，可按第 1.1 节降级为「只显示本日」。

**下方：待办区（v0.5 改版）**——**全部未完成待办，一次列出，不折叠、不按目录分区**。`raw/` 与其他非日记来源的待办**并入同一列表**，不单独成段、不加「主题笔记」小标题，仅通过每行的来源路径与行号区分。每行显示：来源路径、行号、待办原文（已剥离完成标记，第 3.2.2 节）、行内标签。点击跳转并定位到行；可在首页直接勾选完成。标题行显示「未完成 N 条」。

**排序规则（v0.5 定版，取代 v0.4 的「按来源文件日期倒序」单句）**：

1. 日记来源的待办按**来源文件日期倒序**（今天在最前）；
2. `raw/` 及其他非日记来源的待办**无日期语义**，统一排在所有日记待办之后，组内按来源文件路径字典序、再按行号升序；
3. **不用文件 mtime 排序**——编辑任何一个 `raw/` 笔记都会让整个列表重排，属于不可接受的行为抖动；
4. 嵌套子项紧跟其父项并保持缩进层级（第 3.2.1 节），父子不因排序分离。

**渲染方式**：全量数据 + **虚拟列表**，首屏与滚动都只渲染视口内的行；**没有折叠按钮、没有「展开全部」**。

**为什么取消折叠（v0.5 修订说明）**：v0.4 的「近 30 天折叠」有两处站不住——① 折叠依据是「来源文件日期」，而 `raw/` 笔记没有日期，其长期待办会被默认藏起来，与第 3.1.1 节「`raw/` 待办计入首页汇总」直接冲突；② 用户的诉求是「一眼看全」，折叠把「全量可及」变成了两步操作。代价（5000 条待办的渲染）由虚拟列表承担，见第 8 章首页渲染指标。

### 4.2 全局待办提取与回写 P0

自动扫描全部 `.md` 文件（含 `raw/`），按第 3.2.1 节语法提取待办；支持按标签过滤、按关键词过滤、按状态过滤。

勾选与取消都通过后端按行回写原文件（**定位与写入规则见第 3.2.3 节的三级解析**，前端不直接拼文件内容）。回写前必须校验该行未处于代码块内。

### 4.3 标签系统 P0

按第 3.4 节构建 1-3 级标签树（统一索引）；点击标签，右侧过滤带该标签（含子标签）的笔记，首页待办同步过滤。

标签随文件变化实时更新，不需要手动维护标签清单；每个标签的笔记数与未完成待办数为 P1。

### 4.4 笔记浏览与渲染 P0

扫描指定文件夹下所有 `.md` 文件（`YYYY/MM/`、`raw/` 与用户既有的其他目录均纳入），点击切换查看；渲染支持标题、列表、代码块、表格、任务列表等常用语法。

**正确显示图片**（双轨解析见第 3.1.3 节）：相对文件自身的写法与相对 notes 根的写法都能显示，由后端静态文件服务提供（安全约束见第 9 章）。

编辑体验见第 5 章：默认 Live Preview，不是纯源码与纯预览的二选一。

### 4.5 全文搜索（v0.3 定版，v0.5 沿用）P0

**匹配方式**：子串匹配，英文不区分大小写、中文按原文逐字匹配；不做中文分词、不做模糊匹配、不做拼音匹配——搜「供应」能命中「供应链」，搜「供应 链」（带空格）按整串处理、大概率无结果，这是已知行为，不算缺陷。

**搜索范围**：笔记正文、标签、待办文本；匹配前剥离行尾完成标记（**剥离边界见第 3.2.2 节**）。`raw/` 下的笔记与日记同等参与搜索。

**排序**：无相关性排序。结果固定按「来源文件日期倒序、同文件内行号升序」排列，保证结果稳定可预期。

**代码块**：代码块内容可搜（SQL 备忘是核心场景），但结果里代码命中默认折叠为一行摘要，展开才看全文，避免一段 SQL 淹没结果页；可用过滤开关「仅看正文」排除代码块。

**索引策略**：不建持久化索引文件。启动时全量扫描建内存索引，文件变化时按文件增量更新；提供手动「重建索引」入口（对应 `POST /api/index/rebuild`，见第 7.3 节），索引与磁盘不一致时以重建为准。索引不落盘，就不会出现索引文件与 Git 互相污染的问题。

**组合过滤**：关键词 + 标签 + 待办状态（未完成 / 已完成 / 全部），结果显示命中文件、行号与上下文片段，点击跳转定位。

### 4.6 基础文件管理 P0

**文件列表按年 / 月分组折叠**（v0.4 新增）：一年约 365 个日记文件，平铺不可用。左侧列表按 `YYYY` → `YYYY/MM` 两级分组，组内按日期倒序；`raw/` 单独一组，组内按文件名排序；`assets/` 仅在查看附件时展示。分组默认展开当前月，其余折叠。

支持手动刷新；文件变化自动监听（竞态与失效兜底见第 5.3 节、10.3 节）。

扫描、搜索、监听一律忽略 `.git` 目录与 `.gitignore` 命中的文件。

## 5. 编辑器方案：Live Preview 与三方竞态协议

结论沿用：参考 Silver Bullet，做「看着像所见即所得、底层仍是纯 Markdown」的 Live Preview，不做 Notion 式真所见即所得——真所见即所得的文档模型是 HTML 或 JSON，存回 Markdown 时 SQL 代码块、多级标签、日程时间这类自定义语法最容易被洗掉，且框架体积与「极轻」定位冲突。Silver Bullet 本身也不是真所见即所得，它用 CodeMirror 6 实现 Live Preview；NotesChain 沿用同一路线。

### 5.1 先把成本说清

编辑器是 MVP 工作量与风险第一项，并按两级交付（见 5.2），排期时按「整个 MVP 的三分之一」预估，不许按「套个 CodeMirror」估。表格、代码块、图片更是边界密集区。

### 5.2 实现方式：CodeMirror 6 + 分级 cleanMode

前端编辑器定为 CodeMirror 6 + Markdown 语言支持；用 decoration 实现 cleanMode：平时隐藏 Markdown 符号、直接显示渲染效果，光标移入哪一行，哪一行露出原文供修改，其余行保持渲染态。

| 元素          | 级别 | Live Preview 表现                                                |
| ----------- | -- | -------------------------------------------------------------- |
| 标题、加粗、斜体、列表 | L1 | 符号隐藏、直接显示效果；光标行显示符号                                            |
| 待办          | L1 | 渲染为可点击复选框，点击即按第 3.2.3 节回写并记完成时间                                |
| 标签、日程时间     | L1 | 标签行内着色、点击过滤；日程时间加粗显示                                           |
| 双链 `[[目标]]` | L1 | 仅双链开启时：命中渲染为可点链接样式，未命中渲染为虚线占位；点击按第 3.5 节跳转或新建；关闭时按普通文本显示                         |
| 代码块         | L1 | 等宽字体加底色，内容不做行内渲染；语法高亮放前端轻量实现                                   |
| 表格          | L2 | L1 阶段编辑态显示源码、预览态渲染表格；L2 才做行内渲染，且光标行必须完整露出源码，单元格编辑不得改动列对齐符之外的字符 |
| 图片          | L2 | L1 显示占位与文件名；L2 行内显示图片本身，加载失败显示破图占位与路径，不静默隐藏                    |
| 链接          | L2 | 显示链接文本、点击打开；光标行显示完整语法                                          |

### 5.3 保存、监听与 Git 的竞态协议

同一个文件有三个写入 / 触发源：编辑器自动保存、外部文件监听、Git 防抖提交。三者不串行化，必然出现自己触发自己、提交到一半文件又变了、监听把刚保存的内容当外部修改等问题。协议如下：

1. **版本号**：后端为每个文件维护版本号 = 文件修改时间 + 内容哈希。读取文件时随内容返回；保存时必须带回版本号。
2. **原子写入**：所有写入先写同目录临时文件，再改名替换；Git 提交只对已完成改名替换的文件执行，永不提交临时文件（临时文件命名须被 `.gitignore` 与监听双重忽略）。
3. **冲突判定**：整文件保存时，版本号与磁盘现状不一致 → 拒绝覆盖，返回冲突，前端弹提示让用户选「重新加载」或「强制覆盖」；不做自动合并。**待办回写是例外**：它按第 3.2.3 节的三级解析尝试重新定位，定位得到则照常写入，定位不到才返回错误。
4. **防自触发**：每次自家写入记录「路径 + 新哈希」；监听事件若哈希与刚写入的一致，直接吞掉，不刷新、不重复入队 Git。
5. **防抖分工（三个时钟互不混用）**：编辑自动保存防抖 800ms-1s；Git 提交防抖 30 秒；监听刷新防抖 300ms。Git 提交开始前先做一次待保存刷盘检查：编辑器有未保存内容时，先保存再提交，顺序不可颠倒。
6. **提交期间再变更**：Git 提交执行中文件又变了，不中断本次提交，新变更自然进入下一轮 30 秒防抖；绝不为了「提交最新版」而锁住编辑。
7. **按文件串行化写入（v0.4 新增）**：同一文件的全部写操作（整文件保存、待办回写、日记新建）在后端**串行执行**；不同文件可并行。理由：整文件保存与行级回写若并发命中同一文件，后写者会覆盖前写者的结果，而版本号检查因两者基于同一版本号快照而双双通过——这正是「行号 + 版本号」方案的固有漏洞，串行化是它的必要补丁。

## 6. Git 自动提交

### 6.1 定位：版本历史，不是备份

必须写进产品、也要让用户看懂的一句话：Git 自动提交防的是「改错、删错、手滑」，防不了「磁盘坏、电脑丢、目录被整体删除」。只有本地仓库、没有远程时，仓库和笔记在同一块盘上，盘没了就全没了。界面在 Git 状态区须常驻一行小字提示：「仅本地版本历史，无远程备份」。定期把仓库复制到另一块盘或加远程，是用户自己的事（后续迭代可做一键加远程指引，MVP 不做自动 push）。

### 6.2 启动检测与降级

启动时运行 `git --version` 检测：检测到才启用 Git 功能；检测不到就降级——笔记、待办、编辑、搜索全部照常工作，仅关闭自动提交，界面明确提示「未检测到 git，版本历史未启用」，不报错、不阻断启动。**注意**：这是运行期降级路径，与第 1.3 节的发布前提不冲突——若实测确认目标环境无 git，本次**不发布**（按红线延期），而不是发一个没有版本历史的版本。

实现方式：直接调用本地 git 命令行，不引入 libgit2 等绑定库，守住单文件与内存目标；Git 是用时才起的短命进程，退出即释放，不计入常驻内存（但计入操作延迟，见第 8 章）。

### 6.3 自动 init 与自动提交规则

**自动 init**：笔记目录不是 Git 仓库时自动 `git init`；若其父目录已是仓库，则直接沿用父仓库，绝不在已有仓库内再嵌套建仓；沿用父仓库时，提交范围只包含笔记目录内的变更，并在提示中说明仓库根在哪。

**提交身份**：提交时用 `-c user.name=NotesChain -c user.email=notes@local` 临时传参完成提交，绝不修改用户的全局或仓库级 Git 配置；用户自己配过身份时，优先用用户自己的，不覆盖。

**不自动 push**：只做本地提交。云桌面网络不稳定，自动 push 失败会反复打扰；远程由用户手工添加，产品不碰。

**防抖与合并**：任何变更（页内保存、待办回写、新建每日文件、外部编辑器改动）统一进入提交队列；停止变更 30 秒后执行一次 `add + commit`，把这段时间内的多次保存合并为一个提交。另设上限：持续编辑超过 5 分钟未停手时，强制提交一次。

**提交信息**：固定格式 `auto: YYYY-MM-DD HH:mm (N files)`，N 为本次变更文件数；不试图生成语义化信息。

**失败处理**：提交失败（如仓库被其他 Git 进程锁住）不阻断编辑，失败原因记入状态区，下轮防抖自动重试；连续失败 3 次后停止自动重试并显著提示。

**界面呈现（MVP 最小集）**：仅在顶部状态区显示「上次提交：HH:mm · 待提交 N 个文件」与第 6.1 节的无备份提示。历史浏览、diff、回滚为 P1。

### 6.4 Git 的四个膨胀与冲突源

| 风险             | 处置（定版）                                                                                                                                                                                                                                                |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 图片等大文件撑爆仓库     | 笔记以文本为主，真正的膨胀源是 `assets/` 里的截图与附件。自动 init 时生成默认 `.gitignore`：忽略临时文件与系统文件，但 `assets/` 默认**不忽略**（忽略就等于图片无版本历史，与防丢目标冲突）——改为设阈值：**单个文件超过 5 MB** 时在状态区提示「大文件进 Git 会让仓库持续变大」，由用户决定是否手工加入 `.gitignore`；产品不擅自忽略用户文件。写入 `.gitignore` 前须在界面告知，这是后端唯一会主动新增的非笔记文件 |
| 同步盘与 `.git` 打架 | 若笔记目录位于 OneDrive 等同步盘内，`.git` 的频繁小文件读写可能与同步客户端互相锁定、甚至把仓库同步坏。处置：检测到路径在常见同步盘目录下时，给出明确警告「不建议在同步盘内启用 Git 自动提交」，并允许用户单独关闭 Git 而保留其余功能；产品不在同步盘上承诺仓库完整性。**待验证**（需在目标环境实测同步行为）                                                                                |
| 嵌套仓库           | 见第 6.3 节：沿用父仓库、只提交笔记目录内变更、不嵌套 init                                                                                                                                                                                                                    |
| 30 秒防抖仍刷屏      | 30 秒合并已大幅降频，但「改一下停一下」的碎步编辑仍可能一天几十个提交。处置：这属于可接受的历史粒度——自动提交的价值就在细；同时提交列表在 P1 的历史视图里按天折叠展示。真正要防的只有「无变更也提交」：每次提交前先查状态，无变更直接跳过，不产生空提交                                                                                                                      |

**提交粒度说明**：日记按天分文件，因此 Git 的版本粒度天然等于天——删错某天的日记可用 `git log -- <该文件>` 精确找到并回滚该天，不会牵连其他日期。这是第 3.1 节「按天分文件」的核心收益之一。

### 6.5 Git 状态接口

`GET /api/git/status`：返回 git 是否可用、是否为仓库、上次提交时间、待提交文件数、最近一次提交失败原因。前端顶部状态区只消费这一个接口；Git 不可用时该接口返回降级状态而非报错。

## 7. 界面与技术要求

### 7.1 界面概要

启动后端后，浏览器打开带 token 的本地地址（见第 9 章），默认进入首页工作台。

顶部：搜索框 + 刷新按钮 + 保存状态（编辑页）+ Git 状态（上次提交时间、待提交数、无备份提示）。

左侧：**文件列表（按年月分组折叠）+ 标签树 + 全局未完成待办入口**。右侧：首页时是日程区（本日 / 本周 / 本月三档，默认本周）、全部未完成待办列表与日程诊断区；进入笔记时是 CodeMirror Live Preview 编辑区；进入 `raw/` 笔记时，编辑区下方可展开**反向链接面板**（列出哪些页面链接到本文，P1，仅双链开启时，见第 3.5 节）。

整体风格简洁，类似现代笔记工具但更轻量；不做主题系统。

### 7.2 后端（Rust）与写入规则

框架：Axum。职责：文件扫描、Markdown 解析、待办与标签提取、双链解析、静态文件服务、文件监听、文件写入、Git 调度。只监听 `127.0.0.1`；编译为单文件可执行程序，前端资源打包进二进制（如 rust-embed），分发时只有一个文件。

笔记目录与端口通过启动参数指定，如 `noteschain --dir D:\notes --port 8090`；不写注册表、不落全局配置。

**写入规则**：原子写入（临时文件 + 改名）；待办回写只改目标行（定位见第 3.2.3 节）；同一文件的写操作串行化（见第 5.3 节第 7 条）；监听防自触发；统一按 UTF-8 读写，疑似 GBK 老文件读取时提示而不是乱码覆盖。

**路径解析规则（v0.4 定稿）**：接口的路径参数以 **notes 根目录**为基准并做根目录包含校验；文件内容中的引用按各自规则解析——图片与附件走双轨（先相对文件自身、再相对根，见第 3.1.3 节），双链路径形式以根为基准（见第 3.5.2 节）。

Markdown 渲染与代码高亮放前端轻量实现，后端不引入 syntect 等重型高亮库，守住内存目标。

### 7.3 API 清单（MVP，v0.5 更新）

| 接口                         | 用途                                                                |
| -------------------------- | ----------------------------------------------------------------- |
| `GET /api/files`           | 文件列表（路径、修改时间），按类型分组                                               |
| `GET /api/files/*path`     | 读取单个文件原文，响应带版本号（mtime + 哈希）                                       |

#### 7.3.1 响应结构与错误码（v0.5 新增，补 v0.4 的空白）

**统一响应包络**：所有接口返回 JSON 对象；成功时业务字段直接置于顶层，失败时固定为：

```json
{ "error": { "code": "conflict", "message": "文件已被外部修改", "detail": { } } }
```

`code` 为稳定的机器可读枚举，`message` 为可直接展示给用户的中文，`detail` 为可选结构化补充。HTTP 状态码与 `code` 一一对应，前端只判 `code`、不解析 `message`。

**错误码表（MVP 全部）**：

| HTTP | code | 触发场景 |
| --- | --- | --- |
| 400 | `bad_path` | 路径越界、含 `..`、绝对路径、符号链接跳出根目录（第 9.2 节） |
| 400 | `bad_request` | 请求体字段缺失或格式非法 |
| 401 | `unauthorized` | token 缺失或错误（含 Cookie 校验失败，第 9.1 节） |
| 404 | `not_found` | 文件不存在 |
| 409 | `conflict` | 整文件保存版本号不一致（第 5.3 节第 3 条） |
| 422 | `todo_relocate_failed` | 待办三级解析无法唯一确定目标行或零匹配（第 3.2.3 节），**禁止写入** |
| 500 | `internal` | 其他未分类错误 |
| 503 | `git_unavailable` | Git 不可用或状态查询超时（降级路径，第 6.5 节；`GET /api/git/status` 返回 200 + 降级字段，不用本码） |

**关键接口的响应字段（定版，前端按此对接）**：

- `GET /api/files`：`{ groups: [{ kind: "diary"|"note"|"asset", year?, month?, entries: [{ path, mtime, size, title }] }] }`；`diary` 组按 `year` → `month` 两级嵌套，`note` 组为 `raw/` 及其他非日记 `.md`，`asset` 组仅在显式请求时返回。
- `GET /api/files/*path`：`{ path, content, version: "<mtime>-<sha256前16位>" }`。
- `PUT /api/files/*path`：请求 `{ content, version }`；成功返回 `{ path, version }`（新版本号），失败返回 `conflict`。
- `GET /api/todos`：`{ total, items: [{ path, line, text, raw_line, tags: [], version, done, done_at? }] }`，`raw_line` 为**去掉完成标记后的整行文本**（第 3.2.3 节回写依据）。
- `PATCH /api/todos`：请求 `{ path, line, raw_line, version, done }`；成功返回 `{ path, line, version }`（回写后的新行号与新版本号），失败返回 `todo_relocate_failed`。
- `POST /api/daily`：成功返回 `{ path, created: true|false, content, version }`；`created=true` 表示本次按第 3.1.4 节模板新建。

**幂等与重试约定**：`GET` 全部幂等；`PUT` / `PATCH` 靠版本号天然防重（重复提交同一版本号会得到 `conflict`）；`POST /api/daily` 幂等（已存在则返回 `created: false`）；`POST /api/index/rebuild` 幂等。

## 8. 非功能要求与性能测法

每个指标绑定基线与测量步骤；测不过时改实现或降级功能，不许改数字凑数。

| 指标     | 标准           | 测量方法（定版）                                                                                  |
| ------ | ------------ | ----------------------------------------------------------------------------------------- |
| 冷启动    | < 1 秒        | 基线机：目标公司云桌面（配置须记录在测试报告中）；从进程启动到首页接口首次返回 200，连续测 10 次取中位数；含 Git 检测耗时                       |
| 空载内存   | **参考目标 < 50 MB**（v0.5 放宽，不作发布门槛） | 启动后空闲 60 秒读工作集；不含浏览器与短命 git 子进程，但报告须注明口径；超 100 MB 须在报告里说明原因与优化项 |
| 打开笔记   | < 200 ms     | 本地盘、单文件 ≤ 200 KB，从点击到 Live Preview 呈现，测 10 篇取中位数；网络盘单独测并单独报告，不与本地盘混报                      |
| 待办汇总   | < 3 秒        | 标准语料：1000 个 `.md` 文件、总量约 20 MB、待办约 5000 条（语料构成须随测试报告存档）；冷启动后首次加载首页计时                      |
| 首页待办渲染 | 首屏 < 500 ms  | 同一语料下，首页**全量**待办列表（v0.5 起不折叠）渲染完成到可交互的耗时；同时验证虚拟列表只渲染视口内行、滚动到底部不掉帧 |
| Git 提交 | 不阻塞编辑        | 标准语料下执行一次防抖提交，前端输入无卡顿感且保存接口不排队；`git status` 在网络盘上的耗时单独测，超时（> 5 秒）时 Git 状态区降级为「状态未知」，不拖住首页 |
| 渲染正确性  | 无乱码、无破图      | 用现有 Silver Bullet 目录全量过一遍：图片逐类抽检，代码块、表格、任务列表各至少 10 个样本                                    |
| 双链解析（开启时）   | 无错链          | 全部 `[[目标]]` 逐个核对解析结果：命中项须指向预期文件；未命中项须渲染为占位；同名冲突须在启动时告警并列出冲突，服务正常启动                                    |


**语料构成调整（v0.4）**：1000 个 `.md` 文件的语料改为「约 730 个日记文件（两年按天）+ 约 270 个 `raw/` 笔记」，总量仍约 20 MB、待办约 5000 条。单文件体积全部 < 200 KB 的前提仍成立。

**前端产物体积（v0.5 推迟，不设 MVP 门槛）**：本版不设硬性预算。先按功能完整实现，收尾阶段统一做精简压缩（CodeMirror 按需引入、高亮语言子集、tree-shaking），届时再定「gzip 后 < 800 KB」这类可测指标并写入 v0.6。理由：功能未定型时设体积上限，会逼着在架构上提前做错误取舍。

无 GPU 依赖；跨平台优先 Windows，兼顾 macOS / Linux。

网络盘是云桌面的常态而非边角：文件监听在网络盘上可能失效，须以手动刷新兜底（第 10.3 节），性能报告里本地盘与网络盘两套数字缺一不可。

## 9. 安全要求

先纠正一个错觉：只绑 `127.0.0.1` 不等于安全。它只挡住了局域网里的其他机器，挡不住同一台机器上的其他进程和用户。公司云桌面常是共享或池化环境：同机任意进程都能请求这个端口，等于能读全部笔记、能调用保存接口改文件、能触发待办回写。笔记里有工作记录与 SQL，这个面不能裸奔。

### 9.1 启动 token（P0）

每次启动生成随机 token，访问地址形如 `http://127.0.0.1:端口/?token=...`；全部 `/api/*` 接口与静态文件接口校验 token，无 token 或 token 错误一律 401。token 只存在于本次进程内存，重启即失效，不落盘。

**静态资源的 token 传递（v0.4 补齐，消解 v0.3 的落地缺口）**：`<img>` 等标签无法携带自定义请求头，因此：

- **首次访问**：浏览器打开带 `?token=...` 的地址，后端校验 query 中的 token 后，**种一个 HttpOnly、SameSite=Strict 的 Cookie**（token 值即 cookie 值；SameSite 写死 Strict，不提供放宽选项），并跳转到不带 token 的干净地址；
- **后续所有请求**：前端 fetch、`<img src>`、`<a download>` 一律走 Cookie，由浏览器自动携带；
- **query token 只作首次引导**：一旦 Cookie 已种，后续带 token 的 URL 一律拒绝并重定向到无 token 地址，避免 token 出现在浏览器历史、Referer 头与截图里；
- token 失效（进程重启）后，Cookie 校验失败返回 401，前端提示「服务已重启，请重新打开启动地址」。

### 9.2 路径穿越防护（P0）

文件读写、图片服务、双链解析的所有路径参数，必须先规范化再校验「落在笔记根目录之内」；含 `..`、绝对路径、符号链接跳出根目录的请求一律拒绝并返回 400。图片服务不得变成「读本机任意文件」的口子——这是本地服务的经典漏洞，测试用例须覆盖 `../`、编码绕过与软链接三种。

**双链路径的额外约束**：双链目标路径同样以 notes 根为基准解析，须走同一套规范化与根目录包含校验；`assets/` 之外的目标若解析后落在根目录外，一律按未命中处理并拒绝创建。

### 9.3 写入面最小化

只有第 7.3 节列出的写接口能改文件；写接口只接受笔记根目录内的 `.md` 路径（新建每日文件、创建双链未命中页、`.gitignore` 为仅有的三项例外，且 `.gitignore` 只由 Git 初始化逻辑触发）。

不做的事：MVP 不做账号体系、不做 HTTPS（本地回环 + token 已覆盖威胁模型）；若未来要监听非回环地址，必须另立安全评审，本版明确禁止。

| 安全抽检                 | 无 token 请求被拒；三种路径穿越用例全部被拒；**新增**：不带 Cookie 直接请求 `/assets/*` 返回 401                                |

### 10.2 不在范围内与后续迭代

**不在范围内**：云同步、多用户协作、插件系统、双向链接的**图谱与关系视图**（双链本身已入 P1，见第 3.5 节）、区块链、移动端 App、Outlook API 集成、真所见即所得编辑器、自动 push、循环待办、优先级与截止日期语义、中文分词搜索。

**后续迭代（P1 以后）**：Git 历史浏览 / diff / 回滚 UI、日历视图、暗色模式、导出、已完成待办归档与统计、标签批量改名与合并、一键添加 Git 远程的指引、搜索中文分词、双链别名与锚点语法。

### 10.3 风险与注意事项

- **网络盘监听失效**：监听不可靠时保留手动刷新兜底，不报错刷屏；Git 状态查询超时按第 8 章降级。
- **外部编辑冲突**：整文件保存以第 5.3 节版本号协议为准，不做合并；待办回写以第 3.2.3 节三级解析为准，定位不到即拒绝写入并提示。
- **同文件并发写**：由第 5.3 节第 7 条的按文件串行化保证；若实现时省略此条，会出现「整文件保存与待办回写互相覆盖且版本号双双通过」的静默数据丢失，属必须覆盖的测试用例。
- **体积与内存**：高亮与渲染放前端，后端不引重型库；新增 Git 调度后复测空载内存，口径见第 8 章。
- **解析边界**：代码块、行内代码、标题中的井号与任务语法一律不参与待办与标签解析，双链的 `[[ ]]` 同理，测试用例须覆盖。
- **双轨解析的歧义**：同一引用两轨都命中且指向不同文件时相对路径优先（第 3.1.3 节），须在渲染日志提示；根基准写法导出到其他工具时图片仍可能失效，属已知限制。
- **名字误解（已处置）**：对外介绍时统一口径——「Chain 是 Git 版本链」，README 与界面关于页各放一句，避免被误读为区块链或图谱产品。

**一句话验收口径**：把现在 Silver Bullet 用的笔记目录原样交给 NotesChain——能打开首页看到本周日程（默认本周，可切本日 / 本月；本日视图含未识别行诊断区）和全部未完成待办（不折叠，含 `raw/` 来源），能按多级标签过滤，能在网页里以 Live Preview 写笔记并勾掉待办（哪怕文件同时被外部编辑过也改对行），改完 30 秒内自动落一个 Git 提交，且已有文件一个字都不用改——MVP 即达标。
